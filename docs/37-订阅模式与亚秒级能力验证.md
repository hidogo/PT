# 37-订阅模式与亚秒级能力验证（L2 逐笔）

> 日期：2026-10-19　范围：云端托管沙盒 + 客户端 PTQuant API + 客户端行情适配器

## 1. 结论（先看这里）

**Ptrade 不存在可供策略使用的 L2 逐笔订阅/亚秒推送模式。**
- 云端沙盒：`tick_data` 固定 3s 回调，`run_interval` 股票最小间隔 3s；两者是策略能拿到实时行的最快节拍。
- 客户端 PTQuant：`stocks_subscribe` 仅订阅行情快照，文档明确主推延迟一般 >3s；无逐笔订阅接口。
- 因此"亚秒级获取涨停逐笔"不可行；平台上限 = 3s 帧内检测（均值 ~1.5s）。

## 2. 云端托管沙盒（strategy.py 运行环境）

| 机制 | 节拍/结论 | 依据 |
|---|---|---|
| tick_data(context, data) | 每隔 3s 执行一次；执行超 3s 丢帧 | docs/03 §tick_data |
| tick_data 的 data[security] | 含 order(最近一条逐笔委托)/tick(快照)/transaction(最近一条逐笔成交)；券商有 L2 才有逐笔字段，可 set_parameters(tick_data_no_l2=1) 关闭提速 | docs/03 §tick_data 参数 |
| run_interval | 股票等其他最小间隔 3 秒（期货 1 秒） | docs/00 §5、docs/05 |
| 订阅 API | 无用户可调用订阅接口；沙盒内部仅对股票池标的订阅 | API 文档全量检索 |

要点：逐笔数据能以"3s 帧推送"形式进到 tick_data 的 data 参数（transaction 字段），但推送本身不是亚秒事件，
也不是可注册回调的订阅通道；`get_individual_transaction` 是拉取式补充（一次最多 200 笔）。

## 3. 客户端 PTQuant API（D:\\gjzq\\ptrade\\Libs\\Python\\api）

| 接口 | 说明 | 依据 |
|---|---|---|
| stocks_subscribe / stocks_unsubscribe | 订阅/取消订阅行情快照；主推延迟一般 >3s；建议盘前/分钟级订阅，tick 级只取数 | PTQuantAPI.pdf、docs/22 |
| get_snapshot | 读内存变量（服务端主推快照） | 同上 |
| get_history | 仅 1m K 线 | 同上 |
| 逐笔订阅 | 无 | PTradeQuantApi.py 全方法清单 |
| pyd 内部符号 create_subscribe_tick_data / subscribe_tick_data_info / thread_tick_data | 引擎内部把快照主推喂给 tick_data() 回调的机制，非用户可调、仍为快照节奏 | PTradeQuantCore.cp37-win_amd64.pyd 字符串 |

客户端行情适配器（QuoteConfig.xml serverId=1012，QuoteLevel=L2，IP 118.31.128.138:9999）确认存在 L2 环境通道，
但策略层未暴露逐笔订阅回调；托管沙盒与客户端分离，云策略也无法挂该 SDK 通道。

## 4. 对本策略的落地结论（v0.20）

- 最快实现：tick_data 3s 帧内优先消费 `data[sec]['transaction']`（帧推送、0 额外 API 调用）判定涨停价成交；
  命中即触发首板打板（src=tx）；推送缺字段时回退 `get_individual_transaction` 拉最近 200 笔兜底。
- 灵敏度上界 = 3s（均值 ~1.5s）；不可做真亚秒。
- 相关代码：strategy.py `_tx_frame_zt_ms`（帧推送优先）+ `_tx_first_zt_ms`（拉取兜底）；自测 T46/T47。
- 需盘中核对：`[l2] tx_row/tx_fields`（字段结构）与 `[firstzt] ... state=first(src=tx)`（触发时点接近真实封板）。
